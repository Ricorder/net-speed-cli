# net-speed-cli

Консольный скрипт на Node.js + TypeScript. Берёт один адрес, последовательно делает к нему
10 запросов, дожидается полного тела каждого ответа и печатает среднее время запроса,
суммарный объём и скорость скачивания.

## Требования

- Node.js 18.17 или новее (нужен встроенный `fetch`). Проверено на Node.js v26.5.0.
- Выход в интернет по http/https.

Скрипт не использует сторонних пакетов в рантайме. `typescript` и `@types/node` нужны только
для сборки.

## Запуск

```bash
npm install
npm run build
node dist/index.js "https://speed.cloudflare.com/__down?bytes=2000000"
```

Можно через npm-скрипт (не забыть `--`, иначе аргумент уйдёт npm, а не скрипту):

```bash
npm start -- "https://speed.cloudflare.com/__down?bytes=2000000"
```

Другие варианты:

```bash
node dist/index.js --help      # справка
node dist/index.js https://images.example.com/heavy.jpg   # тяжёлая картинка
```

## Единицы измерения

Скорость печатается в **двух единицах** сразу:

| Единица | Что значит | Пересчёт |
| --- | --- | --- |
| `Мбит/с` | мегабит в секунду, 10^6 бит/с | байт × 8 / секунд / 10^6 |
| `МБ/с` | мегабайт в секунду, 10^6 байт/с | байт / секунд / 10^6 |

Приставки **десятичные** (СИ), как в сетевых тарифах и у провайдеров: 1 Мбит = 10^6 бит,
1 МБ = 10^6 байт. Двоичные единицы не используем: МиБ = 1 048 576 байт, то есть на 4,86%
больше мегабайта. Скрипт считает и печатает строго десятичные единицы.

Время — в миллисекундах, объём — в байтах и мегабайтах (тоже десятичных).

Соотношение единиц: `1 МБ/с = 8 Мбит/с`. Провайдер обещает «100 Мбит/с» — это 12,5 МБ/с
в лучшем случае.

## Методика замера

1. **10 запросов строго последовательно**, без параллельности: параллельные соединения делят
   один канал и показывают суммарную пропускную способность, а не картину одного
   скачивания.
2. **Дожидание полного ответа.** Таймер останавливается, когда прочитан последний байт тела,
   а не когда пришли заголовки. Байты считаются по chunk'ам при чтении потока, поэтому
   «полный ответ, мс» и «байт» описывают один и тот же интервал.
3. **Сжатие выключено** — запрос уходит с `accept-encoding: identity`. Иначе считался бы
   объём после распаковки. Проба на реальном тексте объёмом 4101 байт: с `identity` сервер
   отдаёт `content-length: 4101` и мы читаем 4101 байт; без заголовка Node получает
   `content-encoding: gzip`, `content-length: 1962`, а после распаковки на чтении всё те же
   4101 байт. Записав прочитанное в статистику, мы сообщили бы о скорости, завышенной
   в 2,1 раза относительно реально прошедших по сети байтов.
4. **Кэша нет.** У `fetch` в Node.js (undici) нет HTTP-кэш-хранилища — повторный запрос
   уходит в сеть. В таблице ниже это видно: каждый из 10 запросов прочитал полные
   2 000 000 байт, время между ними падает за счёт разогрева соединения, а не экономии
   байт. Отдельный флаг `--no-cache` не нужен.
5. **Первый запрос включает рукопожатие TLS.** Он почти всегда самый медленный: в примере
   ниже TTFB первого запроса 571 мс против 65-146 мс у остальных. Остальные запросы
   переиспользуют keep-alive-соединение того же пула undici.
6. **Таймаут 30 секунд на запрос.** Упавший запрос не входит в статистику, но виден
   в таблице как `ошибка` и перечислен в блоке «Ошибки».
7. **Статистика.** Кроме среднего печатаются медиана, минимум, максимум и перцентили p90/p99
   (линейная интерполяция, метод R7 — тот же, что у `PERCENTILE.INC` в Excel и у numpy
   по умолчанию). 10 выборок для p99 мало, цифра близка к максимуму и показана как
   ориентир разброса, а не как гарантия.

### Почему «скорость» считается через суммарный объём / суммарное время

Это единственное число, по которому можно сказать «я скачал 20 МБ за 15,4 с». Арифметическое
среднее скоростей отдельных запросов было бы больше: медленные запросы занимают больше
времени, но получают тот же вес, что и быстрые. При равных объёмах запросов (у нас все 10
запросов тянут один и тот же файл) суммарный объём на суммарное время — это среднее
гармоническое, а оно всегда не больше арифметического. Поэтому заголовком идёт суммарная
скорость, а распределение по запросам (медиана, p90, максимум) — отдельной строкой, чтобы
был виден разброс.

## Коды возврата

| Код | Когда |
| --- | --- |
| 0 | хотя бы один запрос удался; часть упавших перечислена в блоке «Ошибки» |
| 1 | ни один из 10 запросов не завершился |
| 2 | не передан адрес, адрес не разобрался или протокол не http/https |

## Структура

```
src/
  index.ts    разбор аргументов, цикл из 10 запросов, печать таблицы и итога
  measure.ts  один запрос: fetch + чтение тела до конца + два тайминга
  stats.ts    среднее, медиана, перцентили, перевод байт/с в Мбит/с и МБ/с
```

## Что этот замер НЕ измеряет

- **Абонентскую скорость провайдера.** Одна точка, один файл, TCP с медленным стартом:
  на 2 МБ канал не успевает разогнаться. Чтобы приблизиться к тарифу, нужен файл
  в десятки мегабайт и несколько источников.
- **Задержку и джиттер линии** — для этого нужны десятки коротких запросов и статистика
  по RTT, здесь есть только TTFB как косвенный признак.
- **Скорость отдалённого сервера целиком.** Один адрес — это один маршрут, один дата-центр
  и одна очередь на сервере. Другая точка даст другую цифру: чтобы оценивать канал,
  надо мерить несколько источников и сравнивать.
